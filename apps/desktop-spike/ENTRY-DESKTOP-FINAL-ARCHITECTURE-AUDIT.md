## 3. Project-B assessment: production-shaped, with real gaps

Solid: auth (fail-closed), ownership on every route, idempotent message
insert + touchChat, usage via the real recordUsage, model proxy with no
client-supplied URL, generic error mapping, health route, live-verified
abort propagation, vendored DB layer keeps drift visible (md5-diffable).

Missing infrastructure (real, ranked):
- No rate limiting on any route (authed user can loop chats/usage/proxy).
- No structured logging / request ids (Vercel logs only; hard to debug prod).
- No Web-App-Firewall-style request-size guard on the proxy (body forwarded
  as-is to Gateway after JSON parse).
- Preview deployments share production POSTGRES_URL + GATEWAY_API_KEY (env
  targets are ["production","preview"]) — a preview deploy hits PROD data.
- CORS/origin: requireDesktopUser is header-auth (no cookies) so CSRF does
  not apply; origin allowlist lives in the retired backend, not here —
  bearer-token model makes this acceptable.
- Health check is static (no DB ping) — "healthy" does not prove DB reachability.

## 4. Shared-code strategy — recommendation

Evidence: vendored files are byte-identical today; next.config resolveAlias +
tsconfig paths make the seam explicit; the vendored set is 5 files (schema
client sessions usage + 2 type deps); schema.ts pulls SandboxState + skill-ref
types, i.e., Web-coupled types leak inward (handled via stub/aliases).

- Option A (status quo) is SAFE for the next stage: coupling is one-way
  (desktop depends on web files), drift is detectable (md5 compare in CI),
  and no Next.js-specific runtime dependency leaked (only drizzle + postgres).
- Option B (packages/db) is the right eventual move but is a REFACTOR with
  migration/tooling risk; it is NOT required before release. Trigger it when
  (a) web DB files change more than occasionally, or (b) a third consumer
  appears.
Recommendation: Option A now; schedule Option B as tech debt with a drift
check (hash compare in CI) as the interim guard.

## 5. Authentication audit (no redesign; actual weaknesses only)

Lifecycle: token minted by better-auth at sign-in (web's auth_sessions; the
desktop reuses browser-session tokens in the spike) → held in Electron MAIN
memory (handler) → sent per-call via gatewayConfig → Project-B validates
verbatim against auth_sessions with expires_at > now(), JOIN users.

- Expiration: enforced in SQL (fails closed). Revocation: deleting the
  auth_sessions row instantly invalidates (lookup per request). 
- Renderer: cannot see the token (contextIsolation; token lives in main).
- LocalSandbox: agent-run bash sees NO host-added credentials (regression-
  tested); the LAUNCHER env var ENTRY_DESKTOP_SESSION_TOKEN is a spike-only
  convenience — in a packaged app the token must arrive via post-sign-in IPC,
  not env, or agent bash would inherit it. SHOULD FIX before release.
- Identity trust: user identity comes ONLY from the DB JOIN — no
  user-supplied id/email is ever trusted. ✓
- Weakness (actual, minor): tokens are long-lived browser sessions reused by
  the desktop; there is no desktop-specific short-lived token or device
  binding (the retired backend's device-pairing design was the better shape).
  SHOULD FIX before public release; not a blocker for internal next stage.

## 7. Agent execution audit (traced end-to-end)

user text → renderer send → entry:send (fire-and-forget; events stream back)
→ EntryAgentHost.send: turn-scoped AbortController + activeTurn
→ openAgent.stream (prepareCall → sharedProvider(config per call))
→ HTTPS → Project-B /v1/chat/completions → Gateway (streamed through,
req.signal propagated)
→ tool-call events → LocalSandbox.exec/write/read (allowedRoots)
→ approval: tool-approval-request chunk → IPC → renderer → respondToApproval
  → tool-approval-response message → SDK executes/denies (Phase 8 fix)
→ finish → totalUsage accumulate → usage event emitted → POST /usage
→ persistence via /chats + /messages routes (idempotent inserts)

Findings:
- No double usage accounting: one usage event per turn (cancel: 0 events, verified live).
- No double persistence: createChatMessageIfNotExists + upsert-style chat create.
- Cancellation: abort → stopped event; no partial usage; no orphan processes (verified).
- Race (minor): send() has no in-flight guard — two overlapping sends on one
  session would interleave steps and share activeTurn. UI currently prevents
  it. SHOULD FIX.
- stop() nulls activeTurn before the send() finally block runs — benign today
  (abort already fired) but worth an assert. CAN WAIT.
- Stale approval waiters: rejected on abort (Phase 8); renderer crash mid-
  approval leaves the turn awaiting forever → user can Stop. CAN WAIT
  (add approval timeout later).

## 8. Database / persistence audit

Chain verified: sessions.userId ⇐ chats.sessionId ⇐ chat_messages.chat_id;
usage_events.user_id → users (cascade). Desktop and Web use identical code
paths (vendored byte-identical). Concurrent access: unique message ids +
idempotent insert; chat create is get-or-create. 

Cancellation semantics: when a desktop turn is cancelled, NOTHING is
auto-persisted (persistence is explicit, app-layer). A cancelled generation
therefore persists only what the app explicitly appended before the abort —
no partial assistant hallucination rows, no orphan usage. This differs from
Web (Workflow persists the partial message) and is acceptable, but the
product decision "persist partial turns?" should be made before release.
LOGICALLY VERIFIED; partial-persist UX is a product question, not a bug.

Prod hygiene: Phase 9 cleanup removed 12 leftover Phase 7 test chats
(+messages cascade) and 16 test usage_events rows from the production DB.
Production is now free of our test data.

## 11. Performance / resource audit (only real flags)

- Stream pass-through proxying (no buffering) — fine.
- event-stream listeners: one per session, removed on dispose — fine.
- History grows unbounded across a long session (renderer-driven; context
  management is the agent's job — Web has compaction, desktop inherits the
  same agent). CAN WAIT until real chat-length testing.
- exec spreads process.env per call — cheap; fine.
- No leaks found: no ipcMain.on accumulation, no un-removed webContents listeners.

## 12. Security findings (severity-honest)

- CRITICAL: none.
- HIGH: none in code. (Process note: session token + Vercel token from this
  working chat should be rotated — hygiene, not code.)
- MEDIUM:
  1. Launcher-env session token delivery (spike) must become sign-in IPC
     before packaging, else packaged-app agent bash inherits the token.
  2. Preview deployments share prod DB/gateway credentials.
- LOW: no rate limiting; no CSP meta on the harness page (Electron warned);
  static health check; no request-size guard on proxy.
- NO ISSUE: SSRF (no client URLs), secret leakage to renderer/sandbox
  (regression-tested), ownership bypass (per-route checks), CORS/CSRF
  (bearer-token transport), IPC surface (7 invoke-only channels),
  contextIsolation/sandbox enabled.

## 14. Release blockers

MUST FIX BEFORE NEXT STAGE: none.

SHOULD FIX BEFORE RELEASE (concrete, ordered):
1. Token delivery via sign-in IPC (remove launcher-env token path) + desktop-
   specific short-lived token or device pairing (retired backend's design is
   the reference).
2. Real UI shell replacing the harness renderer; persist turns explicitly
   (product decision: partial-turn persistence on cancel).
3. Concurrency guard in EntryAgentHost.send (single in-flight turn per session).
4. Split Vercel env targets (preview must not touch prod DB) or disable previews.
5. CSP on the real renderer page; delete local-agent-test.ts; rotate working-
   session tokens.

CAN WAIT: rate limiting, structured logging, DB-ping health, request-size
guard, history/compaction tuning, approval timeout, deploy alerting, packages/db
extraction (with CI drift-check as interim), agent context-management upstream
test failures (pre-existing drift, untouched files).

NOT A PROBLEM (looks suspicious, is correct): vendored-web duplication
(deliberate, md5-verifiable); plaintext token comparison (better-auth design,
verified); no CORS origin allowlist in Project-B (bearer transport); missing
usage event on cancel (no double-count by design); fire-and-forget entry:send
(events stream over a separate channel); AGENTS.md/CLAUDE.md committed (next-dev
convention).
